# 1. Цель оптимизации

Целью этапа оптимизации является:

- уменьшение токенов промптов (prompt token reduction)
- повышение точности генерации JSON-планов
- снижение вариативности моделей
- улучшение стабильности по JSON-схемам WeekPlan / MealReplacement
- повышение метрик качества по LLM-as-a-judge (GPT-4o-mini)

В результате создаются улучшенные промпты версии **v2**, которые размещаются в:

# 3. Разбор причин проигрыша промптов версии v2

Анализ показал следующие проблемы:

## 3.1 Чрезмерная формализация снижает качество блюда
Промпт v2 для MealReplacement включал фразы:

Название new_dish должно быть коротким (до 4 слов).
Используй минимум слов.


Это приводило к деградации:
- similarity  
- quality  
- preference_match  

Модель выбирала слишком короткие, нереалистичные блюда.

---

## 3.2 Недостаточная контекстность
WeekPlan v2 часто терял meal_type_correctness из-за **слишком короткого описания правил**.

---

## 3.3 Удаление "натурального языка" ухудшило адекватность ответов
LLM-ы парадоксально выдают ЛУЧШИЕ структурированные ответы, когда:

- инструкции **строгие по структуре**,  
- но описание блюд **натуральное и кулинарно правильное**.

v2 удалил много "кулинарных" контекстов про стиль блюд.

---

# 4. Что удалось улучшить в промптах v2

Несмотря на проигрыш по общей метрике, есть существенные улучшения:

### ✔ 4.1 Уменьшение токенов
Промпты v2 короче примерно на **20–30%**, что экономит запросы при продакшене.

### ✔ 4.2 Уменьшение "галлюцинаций"
Промпты v2 лучше следуют JSON-схеме.  
Меньше случаев неправильного поля / структуры.

### ✔ 4.3 Улучшение allergen safety
В обоих тестах v2 улучшил или сохранил высокие оценки по аллергенам.

# 5. Best Practices по оптимизации промптов (с выводами)

На основе проведённых экспериментов определены принципы, которые дают лучший баланс **качества** и **токен-эффективности**.

---

# 5.1 Структура должна быть строгой, но не чрезмерной

❌ плохо:  

Название блюда ≤ 3 слов. Используй минимум слов.

✔ хорошо:  


---

# 5.2 Натуральный язык помогает LLM понимать контекст блюда

Если убрать слишком много “кулинарных” намёков → similarity падает.

---

# 5.3 Использование JSON Schema обязательно

Использовать:

response_format = { "type": "json_schema" }


и явно указывать schema = WeekPlan / MealReplacement.  
Это снижает вариативность в 2–4 раза.

---

# 5.4 Избыток ограничений ухудшает качество

Ограничения типа:

- «до 4 слов»
- «минимум слов»
- «не используй...»
- «не добавляй...»

→ приводят к ухудшению preference_match и quality.

Используй ограничения, только если они обоснованы логикой продукта.

---

# 5.5 Калорийность — оптимально ±10–20%

Слишком строгий диапазон (±8%) → модель чаще ставит NONE  
Слишком свободный (>20%) → ухудшается calorie_match.

Оптимум для MealReplacement: ±15–20%.

---

# 5.6 Предпочтения и аллергии всегда выносить отдельными пунктами

Работает лучше всего:



Предпочтения: ...
Аллергии: ...


а не «Учитывай пожелания и безопасность» (слишком абстрактно).

---

# 5.7 Сохранять баланс между краткостью и смыслом

Лучший стиль — **краткая техническая инструкция + кулинарный контекст для блюд**.

# 6. Выводы и рекомендации

### 📌 Рекомендации по WeekPlan:
- промпт v2 хорош по структуре, но нуждается в добавлении контекстных требований  
- добавить 1–2 примера блюд (few-shot) для meal_type  
- оставить JSON Schema строго

### 📌 Рекомендации по MealReplacement:
- убрать ограничение “до 4 слов”
- вернуть нормальное естественное название блюд
- оставить строгую схему — это даёт стабильность
- ослабить требования “минимум слов”, оставить лаконичность, но не аскетизм
