Этот документ определяет требования к LLM-компонентам системы, метрики качества и операционные ограничения.

## 1. Выбор модели (Model Selection)

- **Модель:** GPT-5-mini (гипотетическая)
- **Обоснование выбора:**
  - **Баланс цена/качество:** Модель предлагает производительность, достаточную для решения большинства пользовательских задач. За 1000 генераций будет потрачено около $7.12.
  - **Скорость:** Генерация ответа у данной модели может занимать от 2 секунд
  - **Специализация:** Модель эффективна для четко определенных, структурированных задач, какой и является генерация планов питания по шаблону с выводом в JSON.

## 2. Требования к производительности (Performance Requirements)

- **Задержка (Latency):** Среднее время генерации полного недельного плана не должно превышать **7 секунд**.
- **Пропускная способность (Throughput):** На этапе MVP система должна выдерживать до **10 одновременных запросов** (10 RPS) без существенного увеличения задержки.

## 3. Метрики качества (Quality Metrics)

Качество модели будет оцениваться на внутреннем тестовом датасете (`evaluation set`) по следующим критериям:

- **M1: Instruction Following Rate (Точность следования инструкциям):** > 90%
  - *Описание:* Процент сгенерированных планов, которые корректно учитывают все заданные пользователем ограничения (цель, калории, бюджет, предпочтения, аллергии).
- **M2: JSON Format Reliability (Надежность формата):** > 99%
  - *Описание:* Процент ответов модели, которые являются синтаксически корректным JSON и проходят валидацию по заданной схеме.
- **M3: Factual Accuracy (Фактическая корректность КБЖУ):** Отклонение < 15%
  - *Описание:* Среднее отклонение суммарной калорийности в сгенерированном плане от запрошенной пользователем.
- **M4: Content Relevance Score (Релевантность контента):** > 4.0/5.0
  - *Описание:* Субъективная оценка адекватности и разнообразия предложенных рецептов (оценивается вручную).

## 4. Ограничения (Constraints)

- **Стоимость (Cost):** Средняя стоимость генерации одного недельного плана не должна превышать **$0.05**.
- **Приватность (Privacy):** Запрещена передача любых персональных данных (PII), не относящихся напрямую к генерации плана (например, email, имя пользователя), в API модели.
- **Масштабируемость (Scalability):** Архитектура должна позволять быструю замену модели на более мощную (например, GPT-5) с минимальными изменениями в коде.

## 5. Данные для тестирования и оценки (Evaluation Datasets)

Для объективной оценки качества `baseline`-модели была разработана двухуровневая система, включающая как проверку генерации итогового плана, так и оценку базовой "пищевой грамотности" модели.

### 5.1. Внутренний датасет для оценки нутриентной точности

Вместо использования внешнего набора данных, для проекта был разработан собственный датасет для проведения специфического теста.

**Цель:** Оценить базовую способность LLM-модели корректно определять пищевые и диетические характеристики блюда по его составу. Это позволяет проверить, насколько хорошо модель будет "считать в уме" КБЖУ и другие параметры, когда будет сама генерировать планы питания для пользователей.

#### Структура датасета

| Столбец | Описание |
| :--- | :--- |
| `ingredients` | **Входные данные:** Список ингредиентов блюда (например, "куриное филе, рис, брокколи, соевый соус"). |
| `category` | **Ожидаемый результат:** Категория блюда (например, "горячее блюдо", "салат"). |
| `calories` | **Ожидаемый результат:** Примерная калорийность блюда. |
| `protein` | **Ожидаемый результат:** Примерное содержание белков (в граммах). |
| `fats` | **Ожидаемый результат:** Примерное содержание жиров (в граммах). |
| `carb` | **Ожидаемый результат:** Примерное содержание углеводов (в граммах). |
| `lac_int` | **Ожидаемый результат:** Бинарный флаг наличия лактозы (`"Да"`/`"Нет"`), ключевой для проверки непереносимости. |

#### Методология оценки

1.  Модели на вход подается **только** содержимое столбца `ingredients`.
2.  С помощью специального промпта модели ставится задача предсказать значения для всех остальных столбцов (`category`, `calories`, `protein`, `fats`, `carb`, `lac_int`).
3.  Предсказанные значения сравниваются с эталонными значениями в датасете.
4.  Рассчитывается средняя точность (accuracy) предсказаний.

#### Ожидаемый результат

Вычисленная точность по этим предсказаниям служит **прокси-метрикой**. Она показывает, насколько можно доверять нутриентным расчетам, которые модель будет производить при генерации полноценного меню для пользователя. Высокая точность на этом тесте означает, что модель обладает хорошими "внутренними знаниями" о еде и способна генерировать более релевантные и корректные планы.

## 6. Preprocessing и Validation

### Preprocessing (Предобработка)

- Удаление лишних пробелов из текстовых полей (`strip()`).
- Приведение к нижнему регистру для упрощения анализа.
- Обработка пустых полей: если пользователь не указал аллергии, нужно передать в промпт `"нет"` или `"отсутствуют"`, а не пустоту.

### Validation (Валидация)

- **Типы данных:** Убедиться, что `calories` и `budget` — это числа.
- **Диапазоны:** Проверить, что `calories` находятся в разумных пределах (например, от 1000 до 6000). Бюджет не может быть отрицательным.
- **Обязательные поля:** Убедиться, что ключевые поля (например, `goal` и `calories`) заполнены.

### 7. Baseline модель (`ml/models/baseline.py`)

**Задача:** Реализовать простейшую, но полностью рабочую `baseline`-модель, которая инкапсулирует основную логику генерации плана питания.

**Ключевые требования:**
- **Реализация основной логики:** Создать класс или функцию, которая принимает пользовательские данные, форматирует промпт и выполняет вызов LLM API.
- **Интеграция с Langfuse:** Каждый вызов модели должен быть обернут в трейсинг Langfuse для обеспечения полной наблюдаемости и возможности дальнейшей отладки.
- **Создание API для model serving:** Логика модели должна быть доступна через API-эндпоинт, готовый для интеграции с Fullstack-частью.

**Результат:** описание реализации, выбор архитектурных решений и результаты первичных тестов **должны быть задокументированы** в отчете: `reports/baseline_report.md`.

### 4. Оценка качества (`ml/evaluation/`)

**Задача:** Создать и запустить фреймворк для количественной оценки качества `baseline`-модели, проанализировать результаты и сформировать план дальнейших действий.

**Ключевые требования:**
- **Создание скрипта для автоматического бенчмарка:** Разработать скрипт, который прогоняет тестовый датасет через модель и рассчитывает заранее определенные метрики качества (например, точность предсказания нутриентов, соблюдение ограничений).
- **Проведение анализа ошибок:** Выявить и классифицировать основные типы ошибок и "галлюцинаций" модели на основе результатов бенчмарка.
- **Формирование плана улучшений:** На основе анализа ошибок составить конкретный и приоритизированный план действий для улучшения модели в следующих спринтах.

**Результат:** все полученные метрики, ключевые выводы, анализ ошибок и план улучшений **должны сведены** в итоговом отчете: `reports/baseline_report.md`.
